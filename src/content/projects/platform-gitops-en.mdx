## What it's about

I want to understand ArgoCD's App-of-Apps pattern not just in theory but in practice, on a realistic setup that could plausibly run in production. The lab consists of two repositories: [demo-app](https://github.com/Spla4sH/demo-app) for the application code (Go API + nginx frontend) and [platform-gitops](https://github.com/Spla4sH/platform-gitops) as the GitOps source of truth watched by ArgoCD.

## What's running

The stack runs end-to-end: `kind create cluster` → install ArgoCD → apply the root app, and ArgoCD pulls the rest from the repo itself. After that, the demo app, the ArgoCD UI and Grafana are reachable in the browser via ingress.

- **App-of-Apps**: a root Application under `clusters/local/bootstrap/` pulls in one Application per infra component (**ingress-nginx, cert-manager, sealed-secrets, monitoring/Grafana**) and per workload
- **In-repo Helm chart** for the demo app – deployments, services, ingress and a NetworkPolicy, with a security context (non-root, verifiable)
- **CI** in `demo-app` builds the container images (frontend + Go API) to **GHCR**, tagged with `latest` and the commit SHA; the GitOps repo references them via `values.yaml`
- The architecture is documented in [ARCHITECTURE.md](https://github.com/Spla4sH/platform-gitops/blob/main/ARCHITECTURE.md)

## Next steps

1. **Automated image bump**: CI already builds and pushes, but the version bump in the GitOps repo is still manual – the last step towards a fully closed pipeline

## Why this project

GitOps promises: drift is immediately visible, rollbacks are a `git revert`, and nothing on the cluster gets changed by hand. Whether that discipline holds up day to day is something you only find out by building the whole setup yourself.
